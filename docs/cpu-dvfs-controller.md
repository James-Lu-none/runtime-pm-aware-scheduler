
# Deadline-aware CPU DVFS controller

The existing pm_runner has a CPU-only --mode dvfs. It reads fixed-frequency
MobileNet costs and the directed transition cost matrix generated by earlier
profiling scripts. No GPU initialization occurs.

Build and run:
```sh
cmake --build build -j4
ctest --test-dir build --output-on-failure
sudo python3 scripts/benchmark_cpu_dvfs.py
```

The script automatically chooses the newest completed cpu-inference-* and
dvfs-transition-* profile directories by name; override them with
--cpu-profile-dir and --transition-dir. It validates kernel/policy, model
hashes, thread count, period and directed transition coverage. Use the same
model files and build configuration as calibration. The runner binary hash
changes because this controller is new; reprofile if ncnn/build flags change.

Default cycle: small/18 ms, medium/45 ms, large/68 ms, large/100 ms.
Each release is 500 ms apart; 60 jobs per policy, four threads.
Compare fixed low cap, fixed high cap, original native governor (ondemand
on the tested Pi), and adaptive. All use the same deterministic frames and
deadline sequence, and all jobs run even when predicted infeasible.
--ablation adds a transition-blind selector (actual switching still occurs).
--native-governors ondemand schedutil adds both if supported.
--repeats 3 alternates run order. --use-max uses measured maximum transition
cost instead of P95. --thermal enables adaptive ceiling hysteresis (55/60 C
by default); leave disabled for primary energy comparison. This is an
application-level cap controller, not a new kernel governor.

At each job release, the controller subtracts elapsed waiting/setup time
from the deadline, enumerates calibrated caps under the thermal ceiling,
and estimates service P95 + directed ready P95 + margin (default 3 ms).
Among feasible configurations it minimizes profiled energy/job. If the
current cap is still feasible, it can hold it for a 250 ms dwell or when
estimated savings are below 5%. Feasibility and thermal ceilings override
hysteresis. If none is feasible, run the fastest predicted allowed option
and log best_effort. Missing transition costs are not invented. The actuator
polls the cap and reported frequency with 100 us requested sleeps and a
100 ms timeout. It fails on unexpected frequency drift rather than
claiming a calibrated state that was not observed. All four cores share
policy0. Switch latency is included in response time, not backend service.
The CSV includes from/target/reported frequency, measured transition time,
prediction, feasibility, reason, thermal ceiling and queue/preparation time.

Energy scores are paced whole-window rail estimates, not isolated inference
energy or a model of transition energy. P95 sums plus margin are heuristics,
not probabilistic or hard real-time guarantees. No predictive pre-switching,
task migration, kernel changes or CPUIdle control is implemented. Active
cooling and native thermal protection remain enabled. Thermal guard aborts
at 75 C (sampled, not a hard thermal limit).

Evaluation uses existing PMIC telemetry with a final idle tail to make the
release horizon identical. Raw integration still includes startup and
restoration and has imperfect window alignment. Compare both deadline
misses and energy, not energy alone; use by_deadline.csv to see tight-job
outcomes. Native baselines are not held at a fixed frequency. Repeated
results and tighter timing alignment are required before claiming savings.

Output: runs.csv, summary.csv, per-policy jobs.csv, telemetry.csv and
by_deadline.csv, plus original_settings.json. The wrapper restores the
original governor/cap on normal exit, exceptions and handled signals.
The C++ actuator also restores its initial cap on normal exit/unwind.
SIGKILL/power loss cannot be handled. Stop other frequency controllers.

## V2: release-aware look-ahead

V1 `--mode dvfs` remains reactive. V2 `--mode lookahead` uses the known periodic release schedule. It selects the next job's target after the preceding job finishes, applies eligible downscales as early as dwell permits, and schedules upscales 150 ms before the next release (configurable). Only the predicted unhidden transition cost enters the deadline estimate. No extra idle parking cycles are introduced if the next job stays at the same high cap. The 150 ms initial lead is an engineering starting point based on the prior observed ~128 ms tails, not a guaranteed bound. All benchmark policies get the same 200 ms initial release offset. The experiment continues at 500 ms periods and uses the same models and deadlines.

```sh
cmake --build build -j4
ctest --test-dir build --output-on-failure
sudo python3 scripts/benchmark_cpu_dvfs.py --lookahead-only
sudo python3 scripts/benchmark_cpu_dvfs.py --jobs 1200 --repeats 3
```

The default comparison now includes lookahead alongside fixed low/high, the native governor and reactive adaptive. `--lead-ms` controls the upscale lead; `--margin-ms` remains 3 by default to preserve the existing initial safety margin. Test larger margins separately: pre-switching can make 2.0 GHz feasible in the model where 2.4 GHz was previously selected. This can improve energy but may reduce actual deadline slack.

New job columns record write time, first cap/frequency readback, elapsed transition, late flag, start/ready timestamps relative to first release (can be negative), overlap with the response critical path, and whether the switch completed before release. A target observed after the 100 ms soft limit is marked late, not reported as on-time success. Recovery is permitted up to max(500 ms, timeout); inability to observe a valid target within recovery aborts the run, and the wrapper restores original settings. Blocking sysfs calls cannot be interrupted by this software timeout. No claim of physical transition latency is made. The new summary includes pre-release switch counts, late transitions, P95 on-path switch delay, goodput and total rail energy per on-time job. Pre-release counts and total/late switch counts are pooled across repeats; switch latency statistics are medians of run-level percentiles.

Use the same thermal settings and arrival pattern when comparing policies. Thermal derivative, independent power budget, online estimation and extra idle parking are deferred; V2 uses the existing optional ceiling and sampled safety abort. This is look-ahead for known arrivals, not a general online predictor. Energy remains approximate VDD_CORE rail integration; startup offset is included in the sampled window. Goodput denominator uses the nominal release horizon. A late transition may be hidden by advance scheduling and still meet the job deadline. All jobs are executed unless the run aborts on invalid hardware state.
